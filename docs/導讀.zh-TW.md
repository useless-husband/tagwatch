# tagwatch 導讀（給初學者）

這份文件用白話解釋 tagwatch 在做什麼，讓你能在面試時自己講出來。讀完應該能回答三件事：它解決什麼問題、它是怎麼
做到的、它有哪些做不到的地方。比較嚴謹的版本在 [DESIGN.md](DESIGN.md)（英文）。

## 它解決什麼問題

寫 C/C++ 程式時常遇到這種 bug：某個變數的值「不知道被誰改掉了」。程式沒有當掉，只是結果不對。要找出兇手，最直接的
辦法是叫電腦幫你盯著那塊記憶體，一有人碰就告訴你是誰。這叫做**資料監看點（watchpoint）**。

現有的兩種做法各有一個大缺點：

- **硬體監看點**（除錯器 LLDB 用的）：CPU 裡只有 4 個位置，最多同時盯 4 個地方。如果你有 500 個同類型的物件，
  不知道哪一個會被改壞，就沒辦法了。
- **保護整個分頁**（`mprotect`）：數量不限，但一次要保護一整頁（Mac 上是 16 KB）。同一頁裡其他幾百個無關的物件
  被碰到也會觸發，幾乎都是誤報，而且非常慢。

tagwatch 用 M5 晶片的新功能 **MTE（記憶體標記）** 做出第三種：數量不限，而且精細到 16 位元組。

## 八個關鍵觀念（各配一個生活比喻）

### 1. MTE：每 16 位元組一把鎖，每個指標一把鑰匙

MTE 把記憶體每 16 位元組切成一格（叫做 granule，粒度），每一格有一個 0–15 的標籤；每個指標的高位元也藏著一個
0–15 的標籤。CPU 每次存取記憶體都會比對：兩個標籤一樣才放行，不一樣就出錯。

> 比喻：置物櫃每一格有個顏色貼紙，你手上的鑰匙也有顏色。顏色對了才打得開。

Apple 原本用它來擋記憶體安全漏洞（鑰匙拿錯櫃子就抓到）。tagwatch 把它拿來做另一件事。

### 2. 監看 = 故意把鎖換掉

要監看一塊記憶體，tagwatch 就把那幾格的標籤改成「程式裡沒有任何指標拿著的顏色」。從此以後，程式裡任何人碰這塊
記憶體都會出錯，而出錯的那一瞬間，CPU 會告訴我們是哪一道指令、哪個位址。

> 比喻：偷偷把某個置物櫃的鎖換掉。誰來開都會卡住，管理員就能記下「幾點、誰、來開哪一格」。

改標籤只要一道指令（`STG`），而且程式可以改自己的記憶體，不需要任何特殊權限。

### 3. 出錯之後要活下來：假裝自己正在被除錯

在 macOS 上，標籤比對失敗的程式會被系統直接殺掉。唯一的例外是「正在被除錯器追蹤」的程式：這時錯誤會變成一則可以
處理的通知。所以 tagwatch 讓目標程式對系統說「請讓我的父行程追蹤我」（`ptrace(PT_TRACE_ME)`），父行程就是
`tagwatch run`。

> 比喻：工廠規定機器一異常就斷電，但「檢修模式」下異常只會亮燈。我們把機器切到檢修模式，再派一個人站在旁邊。

代價是：被追蹤的程式每收到一個訊號（signal）都會先停下來，等父行程說「繼續」。所以父行程要一直待著轉送訊號，
這就是 `src/supervise.c` 在做的事。

### 4. 處理錯誤的人住在程式裡面

錯誤通知（Mach exception）會送到一個「例外埠」。tagwatch 在目標程式裡多開一條執行緒專門收這些通知。收到之後它
會：查表確認這個位址有沒有被監看、解碼那道指令（讀還是寫、幾個位元組）、沿著堆疊往回走找出呼叫路徑、寫記錄。

> 比喻：警衛室設在大樓裡面而不是隔壁棟。要換鎖、要調監視器畫面都方便，反應也快。

我實際量過把警衛室放在另一個行程的做法：可行，但比較慢（7.9 微秒對 4.7 微秒），而且很多事從外面做不到（例如換
標籤只能在行程裡面做）。

### 5. 最難的一步：放行這一次，但鎖不能換回去

記錄完要讓那道指令真的執行完。最直覺的做法是「把鎖換回原樣 → 讓它執行一步 → 再把鎖換掉」。這有兩個問題：慢
（要出錯兩次），而且鎖換回去的那一瞬間，**別的執行緒**可以溜進來碰這塊記憶體而不被發現。

tagwatch 的做法是：CPU 有一個開關叫 TCO，打開時「只有這條執行緒」暫時不做標籤比對。所以 tagwatch 替每一道出錯
的指令產生一小段程式碼：

```
打開 TCO（只對我自己關掉檢查）
執行原本那道指令
關掉 TCO
跳回原本的下一道指令
```

然後讓出錯的執行緒改去執行這一小段。鎖從頭到尾沒換回去，所以別的執行緒照樣會被攔到。

> 比喻：不是把鎖換回來，而是發給這個人一張「只限本人、只限這一次」的通行證。其他人來還是會卡住。

這樣每次存取只要出錯一次，量起來是 4.7 微秒；直覺做法是 14.8 微秒。

### 6. 小段程式碼要放在「跳得回去」的地方

ARM 的直接跳躍指令最遠只能跳 128 MB。所以那一小段程式碼必須放在原指令附近。程式自己的程式碼附近通常有空位；
但系統函式庫擠在一大塊共用區域裡，深處找不到空位。這種情況下小段程式碼的結尾改成「中斷點」，由處理執行緒幫它
跳回去，代價是多出錯一次（9.5 微秒）。

> 比喻：通行證櫃台要設在門口附近；太遠的門，只好請警衛親自帶人走回去。

### 7. 不是所有記憶體都有鎖

只有「有 MTE 的記憶體」才有標籤。系統的 `malloc` 只替小塊記憶體上標籤；全域變數和堆疊完全沒有。tagwatch 的對策：

- **大塊或被指定監看的配置**：由 tagwatch 自己向系統要一大片有 MTE 的記憶體來發放（`src/arena.c`）。
- **全域變數**：把它所在的那一頁「原地換成」有 MTE 的新頁，內容照抄（`src/adopt.c`，我叫它「收編」）。
- **堆疊**：可以收編別的執行緒的堆疊，但編譯器存取區域變數多半用 `[sp, #位移]`，這種存取 MTE 本來就不檢查，
  所以只看得到「透過指標」的存取。這是做不到的部分，文件裡有寫明，也有測試展示。

> 比喻：只有新式置物櫃能換鎖。舊櫃子的東西要先搬進新櫃子（位址不變），才能被監看。

### 8. 核心不吃這一套

如果程式把被監看的緩衝區交給系統呼叫（例如 `read(fd, buf, n)`），去碰記憶體的是作業系統核心。核心碰到標籤不符會
直接殺掉行程，沒有挽回的機會。所以 tagwatch 把常見的幾個呼叫（`read`/`write` 系列）攔下來：先讓核心讀寫一塊
暫時的緩衝區，再自己把資料搬過去，並且記錄「核心碰了這塊記憶體」。沒有攔到的系統呼叫仍然會讓程式被殺，這是
明確列出的限制。

> 比喻：快遞員（核心）沒有通行證也不接受解釋。所以請他把包裹放在門口的暫存櫃，我們再自己搬進去並登記。

## 每個檔案在做什麼

| 檔案 | 一句話 |
| --- | --- |
| `include/tagwatch.h` | 給別人用的 C API：`tagwatch_watch()`、`tagwatch_alloc_watched()` 等。 |
| `src/mte.c` | 唯一真正用到 MTE 指令的檔案：讀標籤、寫標籤、開關 TCO。 |
| `src/wtab.c` | 監看表：給一個位址，回答「這一格屬於哪個監看、原本的標籤是多少」。 |
| `src/watch.c` | 設置／解除監看（換標籤＋更新表格，兩件事用同一把鎖包起來）。 |
| `src/exc.c` | 例外處理執行緒：整個工具的心臟。收通知、判斷、記錄、決定怎麼放行。 |
| `src/tramp.c` | 產生並管理觀念 5、6 講的那些小段程式碼。 |
| `src/insn.c` | 解碼 ARM64 的讀寫指令：位址、寬度、讀或寫。 |
| `src/bt.c`、`src/symtab.c` | 走堆疊、把位址變成函式名稱（自己讀 Mach-O，不呼叫可能卡住的系統函式）。 |
| `src/trace.c`、`src/fmt.c` | 輸出即時記錄和 JSON；完全不用 `malloc` 和 `printf`。 |
| `src/arena.c` | tagwatch 自己的記憶體配置器，包含「釋放後隔離區」。 |
| `src/adopt.c` | 把普通分頁原地換成 MTE 分頁（收編）。 |
| `src/interpose.c` | 攔截 `malloc`、`free`、`read`、`write`、`sigaction` 等函式。 |
| `src/supervise.c` | 父行程的迴圈：等子行程、轉送訊號。 |
| `src/runtime.c` | 初始化、讀設定、公開 API 的實作。 |
| `src/spec.c` | 解析 `size=48,caller=make_node` 這種監看規格。 |
| `cli/main.c` | `tagwatch run / report / check` 指令。 |
| `cli/report.c`、`cli/json.c` | 讀追蹤檔，印出總結和熱度圖。 |
| `tests/unit/` | 不需要 MTE 的單元測試，GitHub CI 會跑。 |
| `tests/mte/` | 需要 M5 才能跑的測試。 |
| `examples/ledger.c` | 示範用的程式，裡面故意藏了一個 bug。 |
| `bench/` | 效能量測，以及拿來比較的另外兩種做法。 |
| `experiments/` | 做設計決定之前寫的小實驗。 |

## 面試可能會問的十個問題

**1. 用一句話說這個專案在做什麼？**
用 M5 的記憶體標記功能做出數量不限、16 位元組精度的資料監看點：誰讀寫了我指定的記憶體，就記下位址、執行緒和
呼叫堆疊。

**2. 為什麼不用除錯器的監看點就好？**
硬體只有 4 個（`sysctl hw.optional.watchpoint` 印出 4）。想同時盯 500 個物件的同一個欄位就做不到；tagwatch 在
測試裡同時監看了 10 萬個物件。

**3. 為什麼不用 `mprotect`？**
它以分頁為單位。我量過：同樣監看 100 個節點，分頁做法攔了約 127 萬次，其中 99.7% 是不相干的存取，整體比 tagwatch
慢 480 倍。

**4. 程式出錯後為什麼沒有被系統殺掉？**
因為目標程式呼叫了 `ptrace(PT_TRACE_ME)`，在系統眼中它正在被除錯，標籤錯誤就變成可以處理的例外。這是觀察到的
系統行為，不是有文件保證的介面，所以 README 把它列為風險。

**5. 多執行緒的時候會不會漏掉存取？**
不會漏掉「會被 MTE 檢查的存取」。關鍵是放行時不把標籤換回去，而是只對出錯的那條執行緒暫時關掉檢查（TCO）。
測試用 8 條執行緒做 36 000 次存取，回報數量分毫不差。

**6. 開發過程中找到過什麼有意思的 bug？**
一個競爭條件：執行緒 A 出錯的通知還在排隊時，執行緒 B 把監看解除又重新設置。處理程式先查表（沒找到）、放開鎖、
再去讀標籤，這時標籤已經被換成新的，於是把正常的存取誤判成「真的記憶體錯誤」而讓程式死掉。修法是把「查表」和
「讀標籤」放在同一把鎖裡面做。這是壓力測試跑了幾十次才抓到的。

另一個是最後審查時找到的死結：設置監看時，會先用一道「允許出錯」的指令試探那一頁能不能上標籤，試探失敗時的
錯誤要靠例外處理執行緒來救，而試探是拿著鎖做的。如果例外處理執行緒剛好在處理別條執行緒的攔截、也在等同一把鎖，
兩邊就永遠互等，整個程式卡死，連訊號都叫不醒。修法是讓例外處理執行緒「絕不等這把鎖」：搶不到就讓出錯的執行緒
重來一次，先去救拿著鎖的那一位；再加一個小機制避免它一直搶不到。`t_threads` 有一段專門重現這個情況的測試，
修之前每次都卡死，修之後約一秒跑完、數字分毫不差。

**7. 每次攔截要多少時間？主要花在哪裡？**
約 4.7 微秒，加上寫 JSON 記錄約 8 微秒。大部分花在核心：一次例外通知加一次回覆。沒被攔的存取只要 0.1 奈秒，所以
監看很常被碰的記憶體會慢幾千倍；這個工具適合盯少數幾個物件。

**8. 它有哪些做不到的事？**
堆疊上用 `[sp, #位移]` 的存取看不到；沒攔到的系統呼叫碰到被監看的記憶體會讓程式被殺；不能附加到已經在跑的
程式；不能用在開了 hardened runtime 或受 SIP 保護的程式；只有 arm64e 或 x86_64 程式碼的程式會被直接拒絕；`fork` 出來的子行程不受監看；只在 M5 和 macOS 27 上
測過。

**9. 這個點子是你發明的嗎？**
不是。用 MTE 標籤不符來追蹤記憶體存取，在 Android/Linux 上已經有論文做過（例如 Noh 等人的 MTE-tracer）。這個
專案的貢獻是在 macOS 上做出能用的工具，並且用 TCO 取代「拿掉標籤再放回去」，讓它在多執行緒下安全。就我所知，
到 2026 年 9 月為止 macOS 上沒有同類工具。

**10. 你怎麼確定它是對的？**
不需要 MTE 的邏輯（指令解碼、監看表、規格解析、JSON、報告）有單元測試，在 GitHub CI 上跑，其中解碼器是拿真正的
組譯器產生的機器碼來對答案。需要 MTE 的部分在 M5 上跑：每種指令形式都實際執行一次，同時檢查「回報的內容」和
「指令的效果」；另外有 59 項檢查用真的程式跑 `tagwatch run`。做不到的情況也寫成測試，證明行為和文件說的一樣。

## 想自己動手試

```sh
make                 # 編譯
build/tagwatch check # 這台機器能不能用
build/examples/ledger                                   # 先看 bug 的症狀
build/tagwatch run -q -w -a caller=customer_new,off=16,len=8 -- build/examples/ledger   # 再找兇手
make test            # 跑全部測試
```

讀程式碼建議的順序：`include/tagwatch.h` → `src/watch.c` → `src/exc.c` → `src/tramp.c`，這四個檔案看懂，
整個機制就懂了。
